# flaky-repro

**اول وادارش کن خراب شود، بعد ثابت کن درستش کردی.** یک اسکیل ایجنت + چکر قطعی برای تست‌های فلیکی — تست‌هایی که گاهی خراب می‌شوند، در CI می‌افتند و ایجنت‌ها آن‌ها را «درست» اعلام می‌کنند در حالی که فقط دو بار سبز دیده‌اند.

## مشکل

ایجنت‌ها معمولا تست‌های فلیکی را بدون اینکه هرگز خرابی را ببینند «درست» می‌کنند: تست را دو بار اجرا می‌کنند، سبز می‌شود و گزارش می‌دهند درست شد. دو بار سبز شدن دقیقا همان چیزی است که نسخه خراب هم بیشتر وقت‌ها تولید می‌کند. ایجنت هیچ‌چیز را ثابت نکرده — و تست هفته بعد دوباره می‌افتد.

ریاضی‌اش، از [این مقاله](https://dev.to/gabrielanhaia/flaky-tests-are-not-a-ci-problem-they-are-an-agent-problem-4akf) (۱۷ اکتبر ۲۰۲۶): تستی که یک بار در هزار بار خراب می‌شود، هنوز در حدود ۶۱٪ مواقع ۵۰۰ اجرا را سبز رد می‌کند. دو بار سبز شدن در هیچ نرخ خرابی‌ای چیزی را ثابت نمی‌کند.

## قرارداد

1. **اول بازتولید کن.** چکر را اجرا کنید تا یک seed خراب و یک دستور replay دقیق بدهد. بدون seed خراب، هیچ فیکی قابل قبول نیست.
2. **مدرک را ثبت کن.** چکر `flaky-report.md` می‌نویسد: هدف، رانر، اجراها، seedهای امتحان‌شده، اولین seed خراب + دستور replay، نرخ خرابی، راهنمای دسته‌بندی.
3. **قبل از درست کردن، دسته‌بندی کن** — وابسته به ترتیب، زمانی، یا وضعیت مشترک. هرکدام جهت درست خودش را دارد (نگاه کنید به `skills/flaky-repro/references/classification.md`).
4. **فیکس‌های ممنوع:** retry، `sleep()`، skip، تایم‌اوت بیشتر، قرنطینه کردن تست بدون issue پیگیری.
5. **درست شدن را ثابت کن.** همان دستور چکری که خرابی را بازتولید کرد، حالا باید با تمام تعداد اجراها سبز شود و exit 0 بدهد. تعداد اجراهای لازم از نرخ خرابی اندازه‌گیری‌شده می‌آید (تقریبا ۵ تقسیم بر نرخ: خرابی ۱ در ۵۰ حدود ۲۵۰ اجرا می‌خواهد؛ خرابی ۱ در ۱٬۰۰۰ حدود ۵٬۰۰۰ اجرا).

## شروع سریع

```bash
# بازتولید: هدف را ۵۰ بار با seedهای مختلف اجرا کنید (پیش‌فرض)
python3 skills/flaky-repro/scripts/flaky_check.py tests/test_api.py

# FAILURE REPRODUCED — first failing seed: 3
# Replay command: PYTHONHASHSEED=3 python -m pytest tests/test_api.py -q

# ... تست را درست کنید ...

# اثبات: همان دستور حالا باید exit 0 بدهد
python3 skills/flaky-repro/scripts/flaky_check.py tests/test_api.py
# 50/50 runs passed — no failure reproduced.
```

کدهای خروج: `0` = همه اجراها سبز شدند · `1` = خرابی بازتولید شد · `2` = خطای استفاده / رانر پیدا نشد (هرگز دستوری حدس نمی‌زند).

## رانرهای پشتیبانی‌شده

| رانر | مکانیزم seed |
| --- | --- |
| pytest | `PYTHONHASHSEED=<seed>` (+ `--randomly-seed` اگر pytest-randomly نصب باشد) |
| Go | `go test -shuffle=on -count=1` (گو فلگ seed ندارد — شماره اجرا ثبت می‌شود) |
| Jest | `jest --randomize --seed=<seed>` |
| Vitest | `vitest run --sequence.seed=<seed> --sequence.shuffle` |

رانر پیدا نشد؟ با `--cmd` یک دستور صریح بدهید:
`--cmd "python3 run_tests.py --seed {seed} {target}"` (seed در متغیر محیطی `FLAKY_SEED` هم هست).

## چه فرقی با ابزارهای فعلی تست فلیکی دارد

ابزارهای کوچک فعلی در این لین فقط تشخیص‌دهنده و تحلیل‌گرند: تست‌ها را چند بار اجرا می‌کنند یا کد را اسکن می‌کنند و گزارش می‌دهند که تستی فلیکی *به نظر* می‌رسد. هیچ‌کدام seed خراب را ثبت نمی‌کنند، دستور replay نمی‌دهند، «بدون seed خراب فیکس ممنوع» را اعمال نمی‌کنند، یا درست شدن را با استرس‌ران با seed ثابت نمی‌کنند. آن قرارداد بازتولید-اول، چیزی است که این اسکیل اضافه می‌کند. لین تکه‌تکه است، نه خالی — این بهترین ورودی لین است، نه اولین ابزاری که به تست فلیکی دست زده.

## تست‌ها

```bash
python3 -m unittest discover -s tests
```

۱۳ تست چکر (فیكسچرهای دستوری قطعی برای پایداری، به‌علاوه تست‌های end-to-end واقعی با pytest که وقتی pytest نصب باشد اجرا می‌شوند) و ۳ تست end-to-end سرور MCP — همه سبز.
